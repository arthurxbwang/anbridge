# ANBridge 首版设计

本版使用 Go 标准库，实现 AllinSSL 的雷池面板部署协议子集和 Nginx 本机部署后端。
不修改 AllinSSL，不修改或重新编译 Nginx，不开放通用 Shell 或配置写入 API。

## 进程与权限

- `serve`：普通用户运行的 HTTPS 接收器。只读取管理接口 TLS 文件、每站点 Token、
  公共信任根和本机配置；写入自己的暂存目录。
- `deployd`：本机 Unix Socket 服务。标准发行版部署时由 root 运行，配置、
  二进制及其路径必须由 root 控制，不能被组或其他用户写入，也不能经过符号链接。
  systemd 进一步约束可写目录及 capabilities。
- 接收器通过 Unix Socket 提交类型明确的请求：站点 ID、数值证书 ID、证书链、私钥。
  帮助进程独立读取受信配置并重新验证证书，不相信接收器的验证结果。
- 一个 Token 只能对应一个站点。接收器被攻破的最坏权限仍包括请求更换所有已配置站点的
  合法证书，但接口不允许提交目标路径、任意命令、Nginx 配置片段或探测地址。
- 本机 root、Nginx 配置和二进制管理员属于受信边界。Nginx 主配置中引入的其他配置
  也必须由管理员维护；ANBridge 不替代操作系统和 Nginx 的访问控制。

管理 HTTPS 端点默认只监听回环地址。跨主机部署时改为管理网地址，并只允许 AllinSSL 来源。
管理端点证书要匹配 AllinSSL 配置的主机名，使用其信任的公共 CA 或内部 CA。
ANBridge 不自动生成随进程重启变化的自签名证书，也不要求忽略 TLS 校验。

## 配置边界

每站点配置固定：

- `id`、独立的 `token_file`；
- 证书必须覆盖的具体域名；通配符证书可以满足具体域名，但配置中不填通配符；
- 专用 Nginx include 路径；
- 一个或多个本机回环地址的 TLS 探测端点与 SNI；
- 可选 `ca_file`：验证业务证书与探测链的信任根。未配置时使用系统根；
  配置后使用该文件中的根，不与系统根隐式合并。

每个必需域名都至少配置一个探测。远程地址、DNS 形式的探测地址和非回环 IP 被拒绝，
避免受控服务被用作通用网络探测代理。首版要求 Nginx 提供可用于检查的本机 TLS 监听端口。

所有路径必须是绝对规范路径，不允许空白、引号、分号等配置元字符。
API 运行状态目录与部署状态目录不能嵌套，受限部署路径也不能置于 API 状态目录。

## 证书与私钥

上传和绑定时分别检查：

- PEM 大小和格式；只接受一个未加密私钥；
- 叶子证书与私钥配对；
- 叶子在前的完整链顺序、签名及配置的信任根；
- 服务端证书用途、当前有效性、最小剩余有效期；
- 所有配置域名的 SAN 覆盖。

叶子指纹是 SHA-256 DER 指纹。版本 ID 根据规范化证书链和私钥共同计算，
因此中间证书链改变也会产生新版本，不能只凭叶子指纹跳过安装。
真实 TLS 探测重新校验证书链及域名，并比较叶子和有序中间链指纹，不复用 TLS 会话。
链指纹忽略自签名信任根的发送/省略差异，但不会把旧的交叉签名中间链当成新链。

## 文件布局与事务

```
/var/lib/anbridge-api/<site>/<numeric-id>.json   # 接收器暂存，包含私钥，0600
/var/lib/anbridge/<site>/state.json             # 提交状态及恢复日志，0600
/var/lib/anbridge/<site>/versions/<hash>/       # 不可变版本，0700
  fullchain.pem                               # 0644；父目录仅部署用户可遍历
  privkey.pem                                 # 0600
/etc/nginx/anbridge/<site>.conf                # 受管理的两条证书路径指令，0640
```

版本先在临时目录中成对落盘，文件及目录同步完成后整体发布。
专用 include 引用不可变版本内的绝对路径，并通过临时文件、`fsync`、`rename` 和
父目录同步替换。没有让 Nginx 在“新证书 + 旧私钥”这类半更新文件之间选取。

标准流程：

1. 全局互斥，拒绝并发激活；使用文件锁阻止多个部署进程或 bootstrap 同时管理状态。
2. 独立校验证书；核对 include 与已提交状态一致，拒绝覆盖外部修改。
3. 保存不可变新版本。
4. **先**持久化包含旧版本和新版本的 pending 日志。
5. 原子切换专用 include。
6. 执行固定 `nginx -p <prefix> -c <config> -t`。
7. 执行固定 `nginx -p <prefix> -c <config> -s reload`。
8. 对全部配置的 SNI 发起新连接，验证真实证书。
9. 持久化已提交状态，清除 pending，再返回成功。

相同版本重复绑定也会检查真实监听端口；只有证书确实已在使用时才跳过 reload。
HTTP 客户端断开不会取消部署事务；部署和回退有独立的有界超时。
请求方超时后应查询状态或重试绑定，不能假定超时就等于没有执行。

## 回退与恢复

- 配置检查前或检查时失败：恢复旧 include，验证旧运行证书，避免重载已知有错的主配置。
- 重载或新证书探测失败：恢复旧 include，重新检查、重载并验证旧证书。
- 回退失败：保留 pending，拒绝后续部署，输出需要人工介入的错误。
- 新证书已验证、但最后提交状态发生 I/O 错误：不宣布成功，也不盲目切回旧 include。
  原子替换可能已经发布新状态，只是目录同步失败；保留新引用使“旧 pending”或“已提交新状态”
  两种落盘结果都可一致恢复。先排查存储，再查看状态或重启帮助进程恢复。
- 帮助进程启动时：先恢复所有 pending 到之前提交的版本，再开放 Unix Socket；
  恢复失败则不启动服务。
- 初次接入必须 `bootstrap` 一张已有、有效且匹配站点的证书作为回退基线。
  bootstrap 不修改业务 server 块，也不执行重载，需要操作者完成一次 include 接入及验证。

状态文件、证书版本及专用 include 应一起备份。不要单独复制 state.json 回滚。
版本目录默认保留，不自动删除旧版本；暂存配额和到期检查限制 API 暂存增长。
过期暂存文件在下一次上传时清理，闲置站点不会在精确到期时自动删除文件。

## 当前范围

首版针对 Linux、systemd、常规本机 Nginx、每站点一组活动证书/私钥。
一个证书可以覆盖多个明确配置并检查的域名。

尚未提供：

- 双 RSA/ECDSA 证书组合、动态证书缓存模式、跨主机事务；
- Nginx Docker 容器管理、Docker Socket、Kubernetes、远程主机执行；
- 通用面板、业务 vhost 管理、在线修改权限范围；
- 自动管理接收器自身 HTTPS 证书；
- 自动清理历史部署版本、Nginx 全局配置备份恢复。

支持常规文件配置的 Nginx，不依赖商业 API 或特定新版 Control API。
这不代表已经覆盖每个发行版、安全策略和 Nginx 构建；目标环境仍需联调。
